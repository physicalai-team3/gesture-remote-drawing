# 01. 아키텍처

## 1. 목표

스마트폰 카메라에 손을 비추면, 노트북 브라우저의 그림판에 **손가락으로 그린 선이 실시간으로** 그려진다.

| 단계 | 사용자 동작 | 시스템 동작 |
|---|---|---|
| ① 기기 페어링 | 노트북 브라우저로 접속하면 **QR 연결 화면**이 뜸 → 폰으로 QR 스캔 | 세션 발급 → 폰 페이지가 같은 세션으로 접속 → 연결되는 순간 브라우저가 **그림판 화면으로 전환** |
| ② 실시간 영상 스트리밍 | 폰 카메라에 손을 비춤 | 폰 브라우저가 JPEG 프레임을 WebSocket으로 전송 |
| ③ 원격 드로잉 및 제어 | 손가락으로 허공에 그림 | 손 좌표 추출 → 제스처 판정 → 그리기 명령 → 그림판 렌더링 |

**제약**
- 노트북에 GPU 없음 → **모든 추론은 CPU**. 무거운 모델(YOLO-pose, 분할 모델) 대신 **MediaPipe Hand Landmarker**(CPU 실시간용, XNNPACK)를 쓴다.
- PC는 **설치 없이 브라우저만** 사용한다. 폰도 앱 설치 없이 브라우저만 사용한다.
- 폰 브라우저의 카메라(`getUserMedia`)는 **HTTPS에서만** 동작 → cloudflared 무료 터널로 HTTPS 공개 URL을 만든다.

## 2. 구성도

```
                         ┌─────────────────────── Docker Compose (노트북, CPU) ───────────────────────┐
                         │                                                                            │
 ┌──────────┐  HTTPS/WSS │  ┌────────────┐      ┌────────────────────────┐                             │
 │ 📱 폰     │──────────▶│  │ cloudflared│─────▶│ Container A (gateway)  │                             │
 │ phone.html│  JPEG 프레임│  │  (터널)     │      │ 웹/보안 서버 · :8000     │                             │
 └──────────┘           │  └────────────┘      │ - 세션·QR 페어링          │   ① POST /v1/detect (JPEG)  │
                         │                      │ - 영상 수신(최신 프레임만) │────────────▶┌──────────────┐ │
 ┌──────────┐  WS        │                      │ - 파이프라인 조율          │◀────────────│ Container B  │ │
 │ 💻 노트북 │◀──────────────────────────────────│ - 그림판 페이지 제공       │  손 랜드마크  │ (vision)     │ │
 │ board.html│ 그리기 명령 │   localhost:8000     │                        │             │ MediaPipe CPU│ │
 └──────────┘           │                      │                        │             │ :8001        │ │
                         │                      │                        │             └──────────────┘ │
                         │                      │                        │ ② POST /v1/interpret (JSON) │
                         │                      │                        │────────────▶┌──────────────┐ │
                         │                      │                        │◀────────────│ Container C  │ │
                         │                      └────────────────────────┘  그리기 명령  │ (gesture)    │ │
                         │                                                             │ 규칙·상태 머신 │ │
                         │                                                             │ :8002        │ │
                         │                                                             └──────────────┘ │
                         └────────────────────────────────────────────────────────────────────────────┘
```

슬라이드의 `A → B → C → A` 화살표는 **데이터 흐름**이다. 실제 호출은 **A가 B와 C를 차례로 부르는 조율(orchestration) 방식**으로 구현한다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **A가 조율 (채택)** | B·C가 서로를 몰라서 **각자 단독 테스트** 가능. 실패 처리·타임아웃이 A 한 곳에 모임. 1인 1컨테이너 분업에 유리 | A→C 호출 1회 추가 (도커 내부망, ~1ms) |
| B가 C를 직접 호출 (체인) | 화살표와 모양이 같음 | B를 테스트하려면 C가 필요. C 응답 형식이 바뀌면 B도 수정 |

## 3. 컨테이너 책임

| 컨테이너 | 한 줄 요약 | 상태(state) | 주요 라이브러리 |
|---|---|---|---|
| **A gateway** | 사람(폰·PC)과 만나는 유일한 창구. 세션, QR, WebSocket, 정적 페이지, B·C 호출 | 세션 목록, 연결된 WS, 최신 프레임 슬롯, 통계 | FastAPI, uvicorn, httpx, qrcode |
| **B vision** | JPEG 1장 → 손 21개 랜드마크 (정규화 좌표) | 세션별 MediaPipe 인스턴스 (VIDEO 모드 추적용) | mediapipe, opencv, numpy |
| **C gesture** | 랜드마크 시퀀스 → 제스처 판정 → 그리기 명령 | 세션별 필터·상태 머신·현재 획(stroke) | 순수 Python (numpy 불필요) |

- **B는 "보는 것"만**, **C는 "판단"만** 한다. B는 그림판을 모르고, C는 이미지를 모른다.
- 좌표는 모두 **0~1 정규화**. 해상도가 바뀌어도 계약이 그대로다.
- 좌우 반전(전면 카메라 거울 효과)은 **C에서 한 번만** 적용한다 (`config.mirror`).

## 4. 프레임 처리 흐름 (1 프레임)

```
폰  ──JPEG──▶ A: 수신, seq 부여, ack 응답, 최신 슬롯에 덮어쓰기 (처리 중이면 이전 프레임은 버림)
              A 워커(세션당 1개): 슬롯에서 꺼냄
              A ──POST /v1/detect──▶ B: 디코드 → MediaPipe → hands[]          (CPU 15~35ms)
              A ──POST /v1/interpret─▶ C: 필터 → 손가락 펴짐 판정 → 상태 머신 → commands[]  (<1ms)
              A ──WS frame_result──▶ 그림판: commands 실행 (캔버스에 선 그리기)
```

**"최신 프레임만" 원칙**: CPU가 밀리면 큐가 쌓여 지연이 몇 초씩 늘어난다. A는 세션마다 **슬롯 1칸**만 두고, 처리 중에 새 프레임이 오면 덮어써서 오래된 프레임은 버린다 (`dropped` 통계로 보임). 그림이 끊기는 것보다 늦게 그려지는 것이 훨씬 불편하다.

## 5. CPU 성능 예산

| 구간 | 목표 | 근거 / 조정 방법 |
|---|---|---|
| 폰 캡처·인코딩 | 480×360 JPEG q0.7, ~20KB | MediaPipe가 내부적으로 192~224px로 줄이므로 큰 해상도는 낭비 |
| 네트워크 (터널 왕복) | 50~150ms | 같은 Wi-Fi면 `PUBLIC_URL`을 LAN 주소로… 단 HTTPS 필요 → 기본은 터널 |
| B 추론 | 15~35ms / 프레임 | `model_complexity` 대신 Tasks API 기본 모델. `num_hands=1`, VIDEO 모드로 손바닥 검출 생략(추적) |
| C 판정 | < 1ms | 규칙 기반. ML 모델 없음 |
| 목표 FPS | 15 fps | `TARGET_FPS`. 노트북이 느리면 10으로 |
| 목표 체감 지연 | < 250ms | 그림판 하단 HUD에 `latency_ms` 표시 |

컨테이너별 CPU 스레드: B는 `OMP_NUM_THREADS=2`, `CV_THREADS=1`. A·C는 I/O 위주라 기본값.

## 6. 보안 (A = "웹/보안 서버")

| 위협 | 대응 |
|---|---|
| 남이 QR URL을 추측해서 내 그림판에 접속 | 세션 ID 6자 + **페어링 토큰**(`secrets.token_urlsafe(16)`)을 QR URL에 포함. 폰 WS 접속 시 토큰 검증 |
| 터널 주소로 그림판·세션 API에 접근 (세션 ID로 토큰 조회, 세션 대량 생성) | 터널 경유 요청(`Cf-Connecting-Ip` 헤더 있음)은 `/phone`, `/ws/phone`, `/health`만 허용, 나머지는 403. 그림판은 노트북 `localhost`에서만 연다 |
| 폰 2대가 같은 세션에 접속 | 세션당 폰 1대. 새 폰이 붙으면 이전 폰 연결을 끊음 (`replaced`) |
| B·C가 외부에 노출 | B·C는 `ports:`를 열지 않음 → 도커 내부망에서 A만 호출 가능 |
| 큰 프레임으로 메모리 공격 | A가 프레임 최대 크기 제한 (`MAX_FRAME_BYTES`, 기본 300KB) |
| 영상 저장/유출 | 프레임은 메모리에서만 처리하고 **디스크에 저장하지 않음** |

## 7. 장애 시 동작

| 상황 | 동작 |
|---|---|
| B 타임아웃/오류 | 해당 프레임 버림, 통계 `errors.b` 증가. 그림판에는 `hand: null`로 처리하지 않고 **그냥 건너뜀** (획이 끊기지 않게) |
| C 타임아웃/오류 | 해당 프레임 버림, `errors.c` 증가 |
| 손이 화면에서 사라짐 | C가 `LOST_HAND_MS`(300ms) 뒤 `stroke_end` 명령 |
| 폰 연결 끊김 | A가 C에 `reset` → 진행 중 획 종료. 그림판에 "폰 연결 끊김" 표시. 그림은 유지 |
| 그림판 새로고침 | `localStorage`의 세션 ID로 재접속 → 같은 폰 연결 유지 |
